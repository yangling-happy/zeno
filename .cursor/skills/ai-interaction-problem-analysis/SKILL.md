# AI 交互问题标准化分析

复杂 AI 交互问题的标准化分析套路：现象描述→预期行为→根因定位→多方案选型→验收标准→技术改造要点，后续同类问题可直接套用这套梳理模板，用户只需要输入现象和元提示词，相关的logs。

在 Zeno 中，AI 能力经 `AiService`（Ark `chat/completions`、重试、TPM 退避、超时、空内容与降级响应）接入。处理「模型行为不符合预期」类问题时，**不要跳步猜结论**；按下面顺序输出，便于复用与交接。

## 何时使用

- 用户只给了：**现象**、**元提示词（或 system/user 片段）**、**相关 logs**（可部分）。
- 需要一次性产出：根因假设、方案对比、可验证的验收标准、与代码/配置相关的改造点。

## 用户应提供的最小输入（可逐项追问）

1. **现象**：谁在什么路径下看到什么（接口、UI、批任务、哪次请求 ID）。
2. **元提示词**：完整或脱敏后的 system/user/工具说明；若有多轮，标注轮次与角色。
3. **日志**：时间序相关行（含 `AiService`、`ARK_*` 配置是否缺失、HTTP 状态、`TPM`/`rate_limit`、超时 `AbortError`、空内容等）。

## 标准化输出模板（必须按此结构与标题输出）

将下列六级标题作为交付物骨架；缺信息处写「待补充」并列出需用户补充的一项。

```markdown
## 1. 现象描述

- 可观测事实（引用日志片段或字段，避免主观概括）
- 影响范围（单次/稳定复现/仅某环境）

## 2. 预期行为

- 产品或调用方定义的「正确」输出/时延/错误形态
- 与现象的差异（一句话对照）

## 3. 根因定位

- 假设树：按可能性排序，每条标注**证据**（日志/代码路径/配置）
- 当前最可能根因（1 条主结论 + 1～2 条备选）
- Zeno 侧优先核对：`ARK_API_KEY` / `ARK_MODEL`（或 `ARK_ENDPOINT_ID`）/ `ARK_BASE_URL`；`AiService` 重试与 TPM 退避；`response.ok` 与 `payload.error`；空 `content`；超时与降级 `getFallbackResponse`

## 4. 多方案选型

| 方案 | 适用条件 | 优点 | 风险/成本 | 推荐度 |
| ---- | -------- | ---- | --------- | ------ |
| A    |          |      |           |        |
| B    |          |      |           |        |

## 5. 验收标准

- 可自动化或可人工逐步验证的检查项（含：成功样例、失败应报错而非静默降级、边界输入）
- 若涉及限流：明确 TPM 场景下的重试次数与最大等待是否可接受

## 6. 技术改造要点

- 需改的文件/模块（例如 `src/modules/ai/ai.service.ts`）与改动类型（配置、提示词、解析、观测、熔断）
- 日志与指标：建议新增的关键字段（requestId、model、latency、retryCount）
- 回滚方式
```

## Agent 执行要点

1. **先对齐事实**：从日志与代码路径确认是「模型真错」「解析/空内容」「HTTP/限流/超时」还是「降级分支」。
2. **根因与方案分离**：根因段只写证据链；方案段再谈取舍，避免混写。
3. **验收必须可测**：每条验收对应具体输入或日志特征，避免「感觉好了就行」。
4. **引用代码**：说明改造点时，用仓库内路径与符号名（如 `fetchWithTimeout`、`getFallbackResponse`），必要时用代码引用格式便于跳转。

## 简短示例（占位）

**输入摘要**：现象「前端偶发拿到固定兜底文案」；元提示词「正常业务问答」；日志含 `AI 调用完全失败` 与 TPM 字样。

**输出**：在「3. 根因」中优先验证 TPM 与重试耗尽后进入 `getFallbackResponse`；在「6. 改造要点」中讨论队列/削峰、延长退避或前端提示与可观测性，与验收中「失败不应伪装成功」对齐。

---

同类问题后续只需重复提供：**现象 + 元提示词 + logs**，并要求 Agent **按本模板全文输出**即可。
